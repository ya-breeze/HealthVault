## Context

This repo (like all projects in this environment) requires proposing an OpenSpec change, getting the spec-only PR approved, then implementing, then archiving the change (`openspec archive --yes`) in the *same* PR before merge. Delta specs under `openspec/changes/<id>/specs/<capability>/spec.md` only record `## ADDED/MODIFIED/REMOVED Requirements`; a `MODIFIED` entry has no diff against the requirement it replaces, and the delta file is new in git, so a reviewer looking at the PR diff sees new prose with no way to tell what changes relative to the current merged spec. `openspec/specs/` (the merged, canonical view) isn't updated until the archive step, which happens right before merge — after the review that matters most.

No CI pipeline exists in this repo, or in any sibling repo in this environment, today. Deployment goes through Portainer git-deploy pulling `main`, not GitHub Actions. There is also no pre-commit hook framework (no husky/lefthook/pre-commit) anywhere in this environment. The only existing task runner is a root-level `Makefile` (currently backend-only targets: `build`, `test`, `lint`, `run-backend`).

## Goals / Non-Goals

**Goals:**
- Let a reviewer read the post-change spec wording directly in the PR diff, for changes touched by that PR.
- Keep delta specs as the sole source of truth; the projection is purely derived, regenerable, and never hand-edited.
- Make it structurally hard to forget: a CI check fails the PR if the committed projection doesn't match what regenerating produces.
- Guarantee `openspec/specs.projected/` never lands on `main` as persistent content — it is a review-time artifact scoped to the PR's lifetime, not a permanent duplicate of `openspec/specs/`.

**Non-Goals:**
- Not changing when deltas actually merge into `openspec/specs/` (still only at `openspec archive`).
- Not building a general diff-viewer or web UI — GitHub's native file diff on a committed file is the delivery mechanism.
- Not *resolving* cross-change requirement conflicts (two touched changes editing the same requirement) — the generator detects and rejects them with an error naming the conflicting change ids and requirement; a human resolves it by editing the deltas. (An earlier version of this design assumed `openspec archive` would reject these itself; reproduced that it does not — see Decision 8.)
- Not retrofitting this into any other repo in this environment. HealthVault is the first; rollout elsewhere is a separate decision.

## Decisions

**1. Scoped to touched capabilities only, with an explicit comparison file — not a full-tree copy.**
An earlier version of this design copied the worktree's entire post-archive `openspec/specs/` tree into `openspec/specs.projected/` on every run. Since `openspec/specs.projected/` never persists on `main` (Decision 4 / Goal 4), there is no git-committed baseline for untouched capabilities to be diffed against between PRs — every PR that touches `openspec/**` would show *all* capabilities (19 on `main` today) as freshly-added files, not just the ones the PR actually changes. Verified empirically against this branch: a full-tree copy produced 20 added files and ~1,989 added lines, almost none of it relevant to this PR's own single new capability. This defeats the goal of a focused, reviewable comparison.

The fix: the script computes the set of **touched capabilities** — the capability directory names under each touched change id's `specs/<capability>/spec.md` — and for each one writes exactly two files:
- `openspec/specs.projected/<capability>/spec.md` — the full post-archive requirement text (from the worktree), for reading the final wording as a coherent whole.
- `openspec/specs.projected/<capability>/spec.diff` — a unified diff (`diff -u`) between the current, unarchived `openspec/specs/<capability>/spec.md` (or `/dev/null` if the capability is new) and the same post-archive text, so the old→new comparison is explicit and doesn't depend on git having a prior commit to diff against.

Capabilities untouched by this PR are not written at all — there is nothing to project for them, and this bounds the artifact's size to what the PR actually changes regardless of how large `openspec/specs/` grows.

**2. Full rebuild of the touched-capability output each run, not incremental sync.**
Within the scoped set from Decision 1, the script still does `rm -rf openspec/specs.projected && mkdir` then writes fresh output per touched capability, rather than incremental patching. This stays trivially idempotent and needs no extra dependency (`rsync` isn't guaranteed present in the CI image or contributors' machines) versus `cp`/`diff`, which are universal.

**3. A disposable detached git worktree, not `git stash` or a second clone.**
`git worktree add --detach <tmp> HEAD` gives an isolated checkout of the exact committed tree without disturbing the primary working tree — critical since the script must be safe to run with uncommitted changes present (confirmed necessary: this repo currently has substantial uncommitted work on an unrelated feature branch at time of writing). A second full clone would be network-bound and slower; `git stash` would require unstashing correctly even on failure and would still mutate the primary tree's index. A worktree shares the object store, is local-only, and is safely disposable via `git worktree remove`.

**4. Rebuilding is based on committed state at HEAD, not the dirty working tree.**
Uncommitted edits to a delta spec are not reflected in the projection until committed. This is a deliberate simplification: reflecting uncommitted state would mean copying dirty files into the worktree (or running the CLI directly against the primary tree, which conflicts with keeping the primary tree undisturbed and unblocked for the multi-change / zero-change cases). Documented as "commit your delta edits, then regenerate."

**5. The `openspec/specs.projected/` lifecycle is derived purely from "which change ids are currently touched," with no separate "is this the final archive commit" flag.**
When a PR is mid-review, its delta specs live under `openspec/changes/<id>/specs/**`, so the diff-based detection finds them and the script populates the projection. When the same PR later runs the real `openspec archive <id> --yes` (per this repo's existing workflow, before merge), the delta moves to `openspec/changes/archive/<date>-<id>/`, which no longer matches the `openspec/changes/*/specs/**` glob (the glob's single `*` can't match the two path segments `archive/<date>-<id>`). Re-running the generator at that point finds zero touched ids and wipes the projection back to empty — the exact state needed before merge. One code path handles both directions; no special-casing archive vs. non-archive runs.

**6. CI enforces via regenerate-and-diff against the staged index, not a bespoke "is this stale" heuristic — and not a plain working-tree diff — staged from an existing parent path.**
The workflow runs the identical script contributors run locally, then `git add -A -- openspec && git diff --cached --exit-code -- openspec/specs.projected`. Staging before diffing is required, not cosmetic: a plain `git diff --exit-code -- openspec/specs.projected` only compares tracked files and silently ignores untracked ones, so a PR that omits `git add`ing the regenerated output entirely — the exact failure mode this check exists to catch — would pass with exit 0. Staging first (which also stages needed deletions when the projection should now be empty) makes the check see additions, modifications, and deletions alike.

The staging pathspec is `openspec`, not `openspec/specs.projected` directly. Reproduced that `git add -A -- openspec/specs.projected` exits 128 ("pathspec ... did not match any files") whenever that directory has never existed on the current checkout — neither on disk nor in git history — which is exactly the correctly-empty final PR state (a change with no touched deltas, or the state right after archiving). That would fail CI on the very state the check is supposed to pass. `openspec/` itself always exists in this repo, so staging from that parent never hits the empty-pathspec case, while the subsequent diff is still restricted to `-- openspec/specs.projected` so it doesn't care about unrelated changes elsewhere under `openspec/`. This is safe because a fresh CI checkout has no other working-tree modifications under `openspec/` besides what the generator itself just wrote (per the "Generation is isolated from the primary working tree" requirement — the script touches nothing else). This keeps the CI gate provably consistent with the local command named in its own error message (`make projected-specs`) — there's no separate logic in CI that could drift from the script's behavior, only a correct diff target.

**7. Bash, not Node, for the script.**
The repo's only root-level tooling is the Makefile invoking shell/Go commands; there is no root `package.json` (the frontend's is scoped to `frontend/`). A bash script matches the existing pattern and avoids adding a Node dependency to run a script whose job is mostly `git` and file operations. The `openspec` CLI itself is a separate, already-required binary.

**8. Cross-change requirement conflicts are detected by the script before archiving, not assumed to be caught by `openspec archive`.**
An earlier version of this design assumed that if two touched changes modified the same requirement in conflicting ways, `openspec archive` would error when the second one ran. Reproduced this against `openspec` 1.6.0 and it is false: two changes each validly modifying the same existing requirement in the same capability (same requirement name, different body text) both pass `openspec validate --strict` individually, and both `openspec archive <id> --yes` calls succeed with no warning — the second archive silently overwrites the first's text. The result is order-dependent (this script archives in lexical change-id order, which need not match the order a maintainer eventually archives them for real), so the projection could show wording that never actually gets merged.

The fix: before creating the worktree or invoking `openspec archive` at all, the script parses every touched change id's delta files (`openspec/changes/<id>/specs/**/spec.md`) for `### Requirement: <name>` headers (under any of ADDED/MODIFIED/REMOVED) and builds a set of `(capability, requirement name)` pairs per change id. If the same pair appears under more than one touched change id, the script exits non-zero immediately — before touching `openspec/specs.projected/` or creating a worktree — naming the conflicting change ids and the requirement. This turns a silent, order-dependent overwrite into a loud, pre-flight failure.

This must also cover `## RENAMED Requirements` sections, which `openspec` 1.6.0 genuinely supports (confirmed in the installed CLI's parser: `- FROM: `### Requirement: <old name>`` / `- TO: `### Requirement: <new name>`` pairs, applied before REMOVED/MODIFIED/ADDED during archive) and are otherwise invisible to a parser that only looks for literal `### Requirement:` header lines — a RENAMED block contains no such header of its own, only FROM/TO lines referencing the old and new names inside backticks. Without handling this, one touched change renaming requirement `A` to `B` while another touched change modifies or removes `A`, or adds `B`, can validate independently per change but silently conflict (or produce an order-dependent result) at archive time, exactly like the un-renamed case Decision 8 already handles. The fix: the parser treats both the FROM name and the TO name of every RENAMED entry as touched requirement names for that change id, alongside the ADDED/MODIFIED/REMOVED names, before computing overlaps.

**9. `spec.diff` uses stable `diff -u --label` headers, not raw file paths.**
Raw `diff -u a b` embeds both input paths and each file's modification timestamp in its `---`/`+++` header lines. Reproduced that this makes the output nondeterministic here specifically: the post-archive file lives inside a freshly created, randomly-named temporary worktree (`git worktree add --detach <tmp> HEAD`), so the "after" path differs on every run even when the underlying content is byte-identical — two back-to-back generations of the same committed state produced `spec.diff` files that differed only in that header line. Since CI regenerates in its own temp worktree (a different random path than whatever a contributor generated locally), the staged-diff drift check (Decision 6) would never match, permanently failing CI regardless of content.

The fix: generate with `diff -u --label "openspec/specs/<capability>/spec.md" --label "openspec/specs/<capability>/spec.md" <before> <after>` — fixed, stable labels naming the canonical spec path instead of either input's real (and in the "after" case, ephemeral) filesystem path. Confirmed `--label` also suppresses the timestamp GNU `diff` would otherwise print, so two generations of identical content now produce byte-identical `spec.diff` output.

## Risks / Trade-offs

- **[Risk]** A contributor edits a delta spec, forgets to regenerate, and pushes → CI's drift check (Decision 6) catches this on any PR touching `openspec/**`, failing with the exact fix command — including the case where the projection is entirely missing/untracked, not just stale. Mitigation: documented in the new `openspec/specs.projected/README.md` and this repo's CLAUDE.md workflow notes.
- **[Risk]** A contributor archives the change (finishing step) but forgets to re-run the generator afterward, leaving a stale non-empty `openspec/specs.projected/` in the final commit → the same CI drift check catches this too: regenerating post-archive independently produces "zero touched ids → empty," which will differ (as a staged deletion) from whatever non-empty content is still committed. No separate mechanism needed.
- **[Risk]** `openspec archive <id> --yes` fails inside the worktree (e.g., a validation error) → the script aborts before touching `openspec/specs.projected/` in the primary tree, leaving it exactly as it was; the error from `openspec archive` is surfaced directly so the contributor can fix the delta and rerun.
- **[Risk]** Two changes touched by the same PR modify the same requirement → caught by the pre-archive conflict check (Decision 8), which exits non-zero before any archive call, naming both change ids and the requirement. Resolving the actual conflict (deciding which change's wording should win, or splitting the requirement) is a human decision, not automated by this script.
- **[Risk]** A correctly empty final PR state (no touched changes, or right after archiving) → the CI drift check (Decision 6) stages from the existing `openspec` parent path rather than the possibly-nonexistent `openspec/specs.projected` path, so it never hits the empty-pathspec error and correctly passes on this state instead of failing it.
- **[Trade-off]** The conflict check (Decision 8) only compares requirement *names* per capability (including both endpoints of any RENAMED pair), not semantic overlap below that granularity — two changes editing genuinely disjoint scenarios under the same requirement name are still flagged as conflicting. This is deliberately conservative (false positives are a script failure with a clear message; false negatives would be silent wrong output).
- **[Trade-off]** Scoping to touched capabilities (Decision 1) means a capability's projection genuinely disappears from the PR the moment nothing under it is touched anymore (e.g., a contributor reverts an edit to one capability's delta while keeping others) — there is no "sticky" projected view of a capability once its own delta stops changing it. This is intended: the projection always answers "what does this PR currently change," not "what has this PR ever touched."
- **[Trade-off]** `spec.diff` is generated fresh via `diff -u --label` each run rather than derived from git history, so it does not distinguish "changed since last regeneration" from "changed since the current merged spec" — it is always base-vs-current-worktree, which is the comparison that matters for review but means re-running the script mid-review does not produce an incremental diff-of-a-diff.
- **[Trade-off]** GitHub's `linguist-generated=true` collapses the projection in the PR's "Files changed" view by default (reviewers must click to expand), rather than hiding the diff entirely (`diff=false`, which was deliberately not used) — a small extra click, in exchange for the diff still being fully visible and searchable when needed.

## Migration Plan

No data migration. Rollout is additive:
1. Land the script, Makefile target, `.gitattributes` entry, and docs first (no CI yet) — a no-op for any PR that doesn't touch `openspec/**`.
2. Add the CI workflow last, once the script is verified to behave correctly by hand (including the zero-change and multi-change cases) against this change's own PR.
3. No rollback beyond reverting the added files; nothing else in the repo depends on `openspec/specs.projected/` existing.
