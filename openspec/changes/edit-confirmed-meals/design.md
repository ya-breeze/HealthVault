## Context

`photo-food-nutrition-logging` (archived) shipped photo upload, vision recognition, clarification, item resolution, and confirm. Once confirmed, a meal's items are permanently locked: `PatchMealItem` (`backend/pkg/server/food_item.go`) returns 409 for a `confirmed` meal, and `ReviewClient.tsx` renders `MealItemRow` with `readOnly={meal.status === 'confirmed'}`. The meal's macro aggregate (`FoodMeal.Aggregate`) is computed exactly once, inside `ConfirmMeal`.

There is also no way to browse past meals: `GET /api/food/meals/{id}` (owner-scoped) exists but nothing lists meal IDs for a user. The only entry points are the direct link from the upload flow and a hand-typed URL. The generic `GET /api/data/food_meal` table (family-visible, no items/photo) shows rows with no links out.

`RetryMeal` (`backend/pkg/server/food_retry.go`) already re-runs vision analysis on a stored photo and fully replaces items via `persistAnalysis`, but only for `failed` or stale-`processing` meals, with no way to give the model new information, and — like `ClarifyMeal` — unconditionally marks the meal `failed` on error. That is safe for `Retry`/`Clarify` today because every state they can be called from (`failed`, stale-`processing`, `pending_clarification`) has nothing valuable to lose: there is no reviewed, edited, or confirmed content sitting behind it. `Reanalyze`, introduced by this change, is eligible from `pending_review` and `confirmed`, where that is no longer true — falling back to the same unconditional-`failed` pattern there would destroy a usable, possibly user-edited meal because an optional correction attempt failed. This surfaced in review of the first draft of this design and is addressed explicitly below.

**Round 1 review findings.** A first review pass on this change surfaced the following gaps, all incorporated into the decisions below: (1) `Reanalyze`'s eligibility check was a read-then-act race, not an atomic claim; (2) `Reanalyze` had no non-destructive failure path; (3) stale clarification state could leak into a fresh reanalysis; (4) a reanalyzed confirmed meal would carry forward its old aggregate; (5) "recompute aggregate after edit" described two separate writes, not one transaction; (6) the frontend plan only updated the edited item, not the meal aggregate, so totals wouldn't refresh live; (7) cross-user (IDOR) test coverage was missing for the new mutation endpoints; (8) the recent-N history cap directly contradicted the "find any past meal" goal; (9) the history endpoint was specified to return raw `FoodMeal` rows, leaking `photo_path`/`raw_response`/`clarify_log`; (10) meal PATCH didn't preserve the "non-zero `logged_at`" invariant; (11) history ordering by `logged_at` alone is non-deterministic given ties; (12) `?limit=` had no defined behavior for invalid/non-positive values (and GORM's `Limit(-1)` cancels the limit entirely); (13) item creation reused PATCH's validation, which is only sound because a PATCH target already has state — creation could silently produce a nameless or 0g item; (14) the reanalysis hint had no size bound.

**Round 2 review findings** (on the round 1 fixes): (1) `ListMeals`'s "defer the whole tied group" fix still split a group larger than the page limit, reintroducing the loss it was meant to prevent — replaced with the exact keyset cursor described in Decisions below; (2) `ConfirmMeal`/`PatchMeal` wrote unconditionally by id, letting a concurrent `Reanalyze` claim be silently overwritten; (3) `Reanalyze`'s claim matched any eligible status rather than the one actually captured, so a concurrent `ConfirmMeal` transition could be claimed and then reverted to a stale value on failure; (4) `persistAnalysis`/`appendPendingQuestions` swallowed errors internally (`failMeal`) instead of returning them, so a persistence failure downstream of a successful vision call was invisible to `Reanalyze`; (5) `CreateMealItem`/`PatchMealItem` accepted ambiguous source combinations (manual + reference, or two reference IDs); (6) the hint length check counted UTF-8 bytes, not characters; (7) the reanalyze control was offered for photo-less manual meals, which always 409; (8) E2E coverage for several required flows was thin or absent.

**Round 3 review findings** (on the round 2 fixes): (1) the frontend never actually sent `before_id` — the lossless backend cursor was built and tested but the only production caller still used the lossy timestamp-only path, so the real bug remained live; (2) `ConfirmMeal` aggregated from the item snapshot loaded at the very start of the handler, before any write — a concurrent pending-review item edit (which doesn't touch this meal's status) could commit in between and be missed, since the status-only conditional write from round 2 doesn't detect an item-only change; (3) `persistAnalysis` and `appendPendingQuestions` were still two separate statements — a failure in the second left the first's write (items, status, raw_response, zeroed aggregate) committed while `revertReanalyze` only restores status/clarify fields, contradicting the "meal is unchanged" claim on 502; three items (a stale `openspec/specs/food-photo-recognition` decision, `?limit=` invalid-value handling, and history ordering) were re-flagged but already correct — confirmed against the current spec/code rather than changed again.

**Round 4 review findings** (on the round 3 fixes): (1) `Reanalyze`'s exact-status claim still didn't account for `RetryMeal`'s own stale-processing eligibility — a slow `Reanalyze` attempt crossing the same vision-timeout threshold `Retry` uses to judge staleness lets a concurrent `Retry` legitimately claim the meal, and the old unconditional revert would then stomp that newer claim; fixed with the lease-token mechanism described in Decisions below, extended to `Retry` and `ClarifyMeal` too since they participate in the same `processing` state space; (2) the "Load older" E2E test had no `try/finally`, so a failed assertion mid-test (or partway through seeding 51 meals) would leak them permanently into the shared WIP account, and its final assertion assumed exactly two pagination clicks would exhaust the account regardless of pre-existing history; (3) the frontend's `hasMore` heuristic (`rows.length > 0`, correct for round 2's abandoned "defer tied group" design) was never updated back to a simple `rows.length === PAGE_SIZE` check once round 3 replaced that design with an exact keyset cursor that never defers rows; (4) the reanalyze E2E coverage still depended entirely on live, non-deterministic vision output for both success and failure outcomes — added deterministic `page.route()`-mocked tests for both, keeping the live-provider test as supplementary smoke coverage; (5) the `food-photo-recognition` spec's Reanalyze requirement still described the round-1 `status IN (...)` claim rather than round 2's exact-status claim, and didn't mention the lease token at all; six items (two stale spec/limit findings, three already-fixed round-2/3 items, and the cursor-contract sync now folded into this same round's spec update) were re-flagged but verified already correct or addressed as part of this round's changes.

**Round 5 review findings** (on the round 4 fixes): (1) `Reanalyze`'s frontend mapped its new lease-lost outcome to the same `ReanalyzeFailedError`/502 handling as a genuine "meal unchanged" failure, hard-coding an incorrect guarantee and leaving a stale meal on screen — the backend now returns a distinct HTTP 412 for lease loss, and the frontend refetches on it instead of trusting the prior view; (2) `CreateMeal`/`RetryMeal`/`ClarifyMeal` still responded with their own local (and, when superseded, stale) `meal` struct regardless of whether their write actually applied — `analyzeMeal`/`failMeal` now report whether their write applied, and all three handlers reload the real current state before responding when it didn't; (3) the 51-meal "Load older" E2E test's final assertion ("hides after this click") depended on the shared account having fewer than ~49 older meals of its own — removed that assertion from the real-data test and added a fully isolated, mocked test for the short-page-hides-the-button behavior itself; (4) `deleteMeal` never checked its response status, so a failed cleanup call (expired session, 500) would silently leak meals while the test still reported green, and a sequential cleanup loop would abandon remaining IDs after one throw — `deleteMeal` now verifies success and `deleteMeals` attempts every ID via `Promise.allSettled` regardless of individual failures; (5) design.md's own "Reanalyze claims the meal atomically" decision still described the round-1 `status IN (...)` claim, contradicting the lease decision immediately below it — corrected. Five findings were re-flagged but verified already correct against current code (atomic claim documented with the lease, `?limit=` handling, photo-gated reanalyze control, exactly-one-source validation, the aggregate-rollback test).

**Self-discovered fix, between round 5 and round 6**: `ReanalyzeFailedError`/`ReanalyzeSupersededError` (round 5's 502/412 distinction) extended the built-in `Error` class without restoring the prototype chain, so `instanceof` checks against them silently returned `false` after Next.js's production build transpilation — `ReanalyzeControl` was falling through to its generic error branch on every 502/412 response, surfacing the raw backend error text instead of the intended UI copy. Found via a genuine E2E failure on the 412 case; the sibling 502 test had been passing only because its assertion (`getByText('Reanalysis failed')`) happened to match both the intended message and the raw fallback text. Fixed with explicit `this.name` tagging and `Object.setPrototypeOf` on both error classes, a defensive `instanceof`-or-`.name` check in `ReanalyzeControl`, and a tightened 502 assertion (`'You can try again'`, unique to the custom message) so the same class of bug can't pass silently again.

**Round 6 review findings** (on the round 5 fixes plus the instanceof fix above): (1) `reloadIfSuperseded` fell back to the known-stale in-memory meal when the reload itself failed, so a caller mid-flight when a newer attempt deletes the meal outright got a 200 with a ghost meal instead of a 404 — it now propagates the reload error, and `CreateMeal`/`RetryMeal`/`ClarifyMeal` map it to 404 (not found) or 500 via a shared `writeReloadedMeal` helper; (2) `ReanalyzeControl`'s 412 handler set the "showing its current state" message before the refetch ran, so a failed refetch left the stale pre-reanalysis meal on screen under a message claiming it was current — the message is now only set after a successful refetch, with a distinct stale-state warning on refetch failure; (3) `PatchMealItem`'s reference-bind and weight-only-rescale branches accepted a non-positive `weight_grams` (unlike `CreateMealItem`, which already rejected it), letting `ApplyProfile` persist negative or zero item macros and, via the confirmed-meal aggregate recompute, a negative meal total — both branches now reject `weight_grams <= 0` before scaling, mirrored client-side in `MealItemRow`; (4) the "client-side hint validation" E2E test never actually opened the reanalyze control or submitted a blank hint — it only proved the control is hidden for a photo-less manual meal, leaving the actual blank-submission path covered only by the provider-dependent smoke test, which can skip before reaching it — split into two tests: the original (renamed to state what it actually checks) plus a new mocked test that opens the control on a photo-backed meal, submits blank, and asserts both the validation error and zero POST calls.

## Goals / Non-Goals

**Goals:**
- Let the owner find and open any of their past meals, not just the most recent ones.
- Let the owner edit, add, and delete items on a `confirmed` meal, and correct its `name`/`logged_at`, with the meal's stored totals always reflecting its current items.
- Let the owner supply a free-text hint and have vision re-analyze the stored photo, from `failed`, `pending_review`, or `confirmed`, without risking data loss if that attempt fails.

**Non-Goals:**
- Full cursor/date-picker pagination UI — a simple `before`-cursor "load older" affordance (see Decisions) is enough; a rich paginated browser is future work.
- Preserving or merging manual edits across a *successful* reanalysis — full item replacement, as `Retry` already does. (A *failed* reanalysis attempt, by contrast, must leave the prior items untouched — see Decisions.)
- Giving `Retry` or `Clarify` themselves the same non-destructive-failure treatment — out of scope for this change; they remain as they are today, since nothing they're eligible from has confirmed/reviewed content to lose.
- Family visibility for the new meal list endpoint — it stays owner-scoped like `GetMeal`, unlike the generic `/api/data/food_meal`.

## Decisions

**Owner-scoped list endpoint returning a minimal DTO, not raw `FoodMeal` rows.** `GET /api/data/food_meal` is family-visible and exposes only denylist-filtered raw columns; `GetMeal` (item detail) is deliberately owner-only. Building history on the generic endpoint would let a user see a row they then get 404 opening. A dedicated `GET /api/food/meals` handler, scoped to `claims.UserID` like `GetMeal`, keeps every listed row openable. It returns a purpose-built `MealSummary` DTO (`id`, `name`, `logged_at`, `status`, `calories`), not the full `FoodMeal` struct — the full struct carries `photo_path` (a server-internal path), `raw_response` (the full model JSON blob), `clarify_log`, and tenant metadata, none of which the list view needs, and returning them for up to 200 rows is needless exposure and payload weight.

**History reachability: an exact `(before, before_id)` keyset cursor instead of a hard cap with no way past it.** The original draft capped the list at `limit` (default 50, max 200) with no way to see older meals — directly undermining the "find any past meal" goal once history exceeds the cap. A first cursor design used `before=<RFC3339 timestamp>` alone (`logged_at < before`), then a "fetch limit+1 and defer the whole tied group" refinement — both were found, on review, to still lose meals: a timestamp-only cursor can't tell "already returned" from "shares this exact logged_at but wasn't returned yet," and the defer-the-whole-group fix only worked when the tied group was smaller than the page limit — a group larger than `limit` still had to be split, reintroducing the same loss. The list now orders by `(logged_at, id)` and accepts `before` paired with `before_id`, forming an exact keyset cursor: `(logged_at, id) < (before, before_id)`. This resumes at precisely the next row after whichever one the cursor names, regardless of how many rows tie at that `logged_at` or how that tie group's size relates to the page limit — no fetch-ahead or trim heuristic is needed. `before` supplied alone (without `before_id`) is still accepted as a simpler, non-cursor "meals before this instant" filter for a caller that just wants a date cutoff; the frontend's "Load older" action always supplies both, since it's the one path that needs the lossless guarantee.

**Deterministic ordering: `logged_at DESC, id DESC` — two fields, not three.** Meals can share a `logged_at` (the data model allows it, and the frontend's minute-granularity datetime-local input for correcting it makes ties plausible in practice, not just theoretical). Ordering by `logged_at` alone is nondeterministic at page/cursor boundaries. `id` is the primary key — already unique per row — so `id` alone is already a complete, collision-free tie-break; an earlier draft additionally sorted by `created_at`, which turned out to be unnecessary (two fields fully determine a total order once `id` is one of them) and would have required exposing `created_at` in the wire format for the cursor to reference it, for no added correctness.

**`?limit=` is validated, not silently reinterpreted.** GORM's `Limit(-1)` cancels the limit entirely, so passing a client-supplied negative value straight through would return unbounded history instead of failing safe. The handler parses `limit` itself: absent → default 50; a positive integer ≤ 200 → that value; anything else (non-numeric, zero, negative, or > 200 without a documented clamp) → HTTP 400. (Clamping instead of rejecting was considered; rejecting is preferred so a client never silently gets fewer rows than it thinks it asked for.)

**Item creation gets its own validation, not PATCH's reused guard.** `patchItemRequest`'s "at least one of manual/fdc_id/custom_food_id/weight_grams/name" guard is sound only because a PATCH target already has a name, weight, and macro state — a bare `weight_grams`-only or `name`-only PATCH is meaningful because it's modifying something that exists. Applied to creation, the same guard would accept a nameless item, or a reference-bound item at the zero-value 0g weight. `POST .../items` therefore requires a non-blank `name`, plus exactly one of: `manual: true` with macro values, or `fdc_id`/`custom_food_id` with a `weight_grams > 0`.

**Item mutation + confirmed-meal aggregate recompute is one DB transaction, not two sequential writes.** The first draft described saving the item and then updating the meal as separate writes — if the second failed, the handler would 500 with the item already changed and the meal's stored totals now stale, breaking the stated invariant; concurrent writes to different items of the same meal could also compute from different snapshots and let the last write silently win. Each item-mutation handler (patch/create/delete) now wraps the whole operation in one `db.Transaction`: apply the item mutation, and if the meal's status is `confirmed`, reload its current items *inside the same transaction* and recompute+persist the aggregate before committing. SQLite serializes writers, so a transaction spanning both writes also closes the concurrent-recompute race between two edits to the same meal.

**ConfirmMeal claims before reading items, not after.** The first two rounds fixed ConfirmMeal's *status* being read-then-blindly-written, but not a distinct race in what it aggregates: it read `meal.Items` once, at the very start of the handler, then wrote the aggregate computed from that snapshot conditionally on status. A concurrent pending-review item edit (permitted while `pending_review`, and — correctly — not itself recomputing this meal's aggregate, since only `confirmed` meals get that) could commit in the gap between that read and the write; because the edit never touches the meal's *status*, the status-only conditional write still matched and confirmed with stale totals. The fix leans on SQLite's actual concurrency model instead of a value comparison: only one write transaction is active on the whole database at a time, and that lock is acquired by the *first* write statement, not at `BEGIN`. So the transaction now claims (`UPDATE ... WHERE status = pending_review SET status = confirmed`) *before* reading items, not after — every item read from that point until commit is guaranteed consistent with what gets written, because no concurrent item-edit transaction can even acquire the writer lock until this one finishes.

**`persistAnalysis` and the pending-clarification log write are one transaction, not two statements.** Originally `persistAnalysis` (item replacement, status, raw_response, aggregate reset) and `appendPendingQuestions` (the `clarify_log` write) were separate calls, each its own transaction/statement. `Reanalyze`'s revert-on-failure guarantee assumes `persistAnalysis` either fully applies or changes nothing — but a failure specifically in the *second* statement left the first's write already committed (new items, zeroed aggregate) while `revertReanalyze` only restores `status`/`clarify_round`/`clarify_log`, producing a meal whose status says one thing and whose items/aggregate say another, under a 502 response that claims nothing changed. Fix: the clarify-log content is now computed as pure data (`buildPendingQuestionsLog`, no I/O) before `persistAnalysis` runs, and `persistAnalysis` takes an optional `clarifyLog *string` it writes in the *same* `Updates` call as status/raw_response/aggregate — one transaction, one outcome. This is a no-op shape change for the three existing callers (upload, clarify's non-clarification branch, retry), which never passed a clarify log anyway.

**Item mutation endpoints return the full updated `FoodMeal`, not just the changed `FoodItem`.** The first draft had `PatchMealItem` continue returning only the item, with the frontend splicing it into `meal.items` client-side — which never updates the meal-level aggregate fields `MacroSummary` reads, so a confirmed meal's displayed total would visibly lag behind an edit until a manual reload, even though the backend now stores the correct number. Returning the full meal (items + current aggregate) from patch/create/delete, the same shape `GetMeal`/`ConfirmMeal` already return, lets the frontend replace its whole `meal` state from the response with no extra round trip.

**Reanalyze claims the meal atomically, mirroring `ClarifyMeal`'s pattern.** A plain "read status, check eligibility, then act" is a race: two concurrent reanalyze calls (double-click, two tabs) can both observe `pending_review`/`confirmed`, both bill the vision provider, and then overwrite each other's item replacement with no defined winner; a concurrent item edit could likewise commit against the old item set while a reanalysis is in flight and be silently discarded by the replacement. `ClarifyMeal` already solves this for its own transition with a conditional `UPDATE ... WHERE status = <expected>` before calling the model. `Reanalyze` uses the same technique, but matched against the *exact* `(status, updated_at)` observed when the meal was loaded, not a broader `status IN (...)`, and writing a fresh `updated_at` as this attempt's lease token: `UPDATE food_meals SET status = 'processing', clarify_round = 0, clarify_log = '', updated_at = <lease> WHERE id = ? AND status = <observed status> AND updated_at = <observed updated_at>`. Zero rows affected → HTTP 409, no vision call. Resetting `clarify_round`/`clarify_log` as part of the same atomic claim (rather than as a separate step, or not at all) matches what `RetryMeal` already does for the same reason: without it, a meal that previously went through clarification could skip questions past the old round cap, or mix an old round's questions into the new run. (The exact-match and lease-token details were tightened across rounds 2 and 4 respectively — see the lease decision below for the full rationale and the two hazards it closes.)

**Reanalyze failure reverts to the meal's prior state instead of forcing `failed`.** Because the claim above already captured the meal's prior `status`, `clarify_round`, and `clarify_log` before overwriting them, a vision error can restore exactly those three fields (conditioned on the lease token below still being current) rather than calling the shared `failMeal` (which always sets `failed`). Items and the stored aggregate are never touched by the claim or by a failed attempt — `persistAnalysis`'s delete-and-replace only runs on a *successful* recognition — so a failed reanalysis leaves the meal exactly as a caller would have found it before trying, provided nothing else has claimed it since (see the lease decision below for when that assumption doesn't hold). The handler responds with HTTP 502 and an error body (not 200 with a mutated meal) so the frontend can distinguish "reanalysis failed, nothing changed" from a normal state transition, instead of inferring failure from the meal's status being unchanged.

**A lease token (the meal's own `updated_at`) guards every analysis attempt against being superseded by a newer one.** This handler is *not* the only writer while status is `processing`, contrary to what an earlier draft of this design assumed: `Retry` treats `processing` as retryable once `updated_at` is older than the vision timeout — the same threshold this handler's own vision call runs against. If this attempt's call is slow enough to cross that threshold right as it fails, a concurrent `Retry` can legitimately claim the same meal (fresh `status=processing`, fresh `updated_at`) before this handler's revert runs. An unconditional revert would then stomp that newer claim back to this attempt's stale prior status — while `Retry`'s own call may still be actively replacing the meal's items in the background, now working against a meal whose status claims it's stable and editable. The same hazard applies to `ClarifyMeal`'s claim, which also transitions into `processing`. The fix: every claim into `processing` (`Reanalyze`'s, `Retry`'s, `ClarifyMeal`'s) captures the exact `(status, updated_at)` it observed as an optimistic-concurrency precondition, and writes a fresh `updated_at` as its own lease token. Every later write for that same attempt — `persistAnalysis`'s final update, `failMeal`, `revertReanalyze` — is conditioned on `updated_at` still matching that lease. If a newer attempt has since claimed the row, the lease no longer matches, the write becomes a no-op, and the row is left exactly as the newer attempt is managing it — never stomped by a superseded attempt arriving late. This required threading a `lease time.Time` parameter through `analyzeMeal`/`runAnalysis`/`processRecognition`/`persistAnalysis`/`failMeal`, plus a `CreateMeal`-side capture (the row's `updated_at` right after `Create`, which is that meal's very first lease). Considered and rejected: a dedicated version/attempt-ID column — `updated_at` already changes on every relevant write and needs no schema change, so reusing it as the lease is strictly simpler for the same guarantee.

**Superseded attempts respond with the meal's real current state, and Reanalyze's lease-loss failure is a distinct HTTP status from its ordinary failure.** Two gaps in the lease mechanism's first cut, both about what a *caller* sees, not just what gets persisted: (1) `CreateMeal`/`RetryMeal`/`ClarifyMeal` all finish by returning their own local `meal` struct — but if that attempt's write was superseded, `meal` only reflects the claim it made, never updated since (persistAnalysis's and failMeal's writes both became no-ops). The caller would see a stale, misleading snapshot instead of what's actually stored. Fix: `analyzeMeal` and `failMeal` now return whether their write applied; a shared `reloadIfSuperseded` helper returns the given meal unchanged if it applied, or a fresh reload from storage if not, and all three handlers respond with that instead of their raw local struct. (2) `Reanalyze`'s failure path conflated two materially different outcomes under the same HTTP 502: a successful revert (the meal genuinely is unchanged) and a lease-loss non-revert (a newer attempt owns the row, and may have already changed it — no guarantee holds). The frontend, having no way to tell these apart, applied the "unchanged" messaging and stale display to both. Fix: lease-loss now responds HTTP 412 (Precondition Failed) — the standard code for "your conditional update's precondition no longer holds" — distinct from the 409 already used for "never even claimed it" and the 502 used for "claimed it, failed, successfully reverted." The frontend maps 412 to a distinct `ReanalyzeSupersededError` and refetches the meal instead of trusting its prior view.

**A successful reanalysis run zeros the meal's stored aggregate.** `persistAnalysis`'s existing update only touches `status` and `raw_response`; it does not reset the seven aggregate columns. For every *existing* caller (upload, clarify, retry) that is harmless because the aggregate is already zero at that point — none of those paths can be reached from `confirmed`. `Reanalyze` can be, so leaving the aggregate columns untouched would attach a confirmed meal's old totals to its brand-new, unreviewed item set — a `pending_review` meal that visibly still shows a calorie total, contradicting `MacroSummary`'s own "totals will be calculated when you confirm" copy for that status. Fix: `persistAnalysis` now unconditionally zeros the seven aggregate columns as part of its existing update. This is a no-op for the three current callers and correct for the new one, so there is exactly one item-replacement code path rather than a reanalyze-specific branch in `persistAnalysis`.

**Meal PATCH preserves the non-zero-`logged_at` invariant.** The existing `Meal Logged Time` requirement guarantees every meal carries a non-zero `logged_at`. A naive PATCH that accepts any decoded `time.Time` would let a client (accidentally or via a bare `{}`-shaped bug) send Go's zero time (`0001-01-01T00:00:00Z`), after which the meal silently drops out of every range query that uses `logged_at`. `PATCH /api/food/meals/{id}` therefore rejects a zero-value `logged_at` with HTTP 400, same as an empty `name`.

**Reanalyze hint is length-bounded, and the request body is capped.** The hint is caller-controlled free text forwarded into a metered, context-limited model request; today only blankness is constrained. A max hint length (500 characters — generous for "this is chicken and rice, not berries"-style corrections, small enough to bound prompt cost) is enforced after JSON decode, and the request body itself is read through a small size-limited reader (e.g. 4 KiB) before decoding, so an oversized payload is rejected (413) before any JSON parsing work, let alone a model call.

**Cross-user (404) coverage is required for every new mutation endpoint.** The existing lifecycle test suite verifies 404-on-cross-user-access for every endpoint it covers, on the principle that a new mutation handler is a new IDOR surface until proven otherwise. `POST .../items`, `DELETE .../items/{item_id}`, `PATCH /api/food/meals/{id}`, and `POST .../reanalyze` all need the same coverage as part of their own tests, not left implicit.

## Risks / Trade-offs

- **[Risk]** A confirmed meal being knocked back to `pending_review` by a *successful* reanalysis is a real state change the owner might not expect. → **Mitigation**: the frontend control for triggering reanalysis explicitly warns that current items will be replaced and the meal will need re-confirming; this was confirmed as the desired behavior for the success path. A *failed* attempt, per the Decisions above, causes no state change at all.
- **[Risk]** Wrapping item mutation + aggregate recompute in one transaction, and reanalyze's atomic claim, add a small amount of handler complexity (transaction boilerplate, revert-on-failure logic) beyond the original single-write sketch. → **Mitigation**: this mirrors patterns (`ClarifyMeal`'s conditional claim, transactional replace in `persistAnalysis`) already established in this codebase, not a new pattern.
- **[Trade-off]** The `before`-cursor "load older" affordance is not a general-purpose paginated API — no total count, no jump-to-date. Acceptable for now (Non-Goal above); revisit if it proves insufficient in practice.

## Migration Plan

No data migration — reuses existing tables and columns. Deploy is a normal backend + frontend release; no rollback concerns beyond reverting the branch.
