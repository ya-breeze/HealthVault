## 1. Implement transparent refresh-on-401

- [x] 1.1 In `frontend/lib/api.ts`, add a module-level `refreshPromise: Promise<boolean> | null` for same-tab dedup, plus the constants `AUTH_REFRESH_LOCK = 'hcw-auth-refresh'` and `LAST_REFRESH_KEY = 'hcw:lastAuthRefreshAt'`.
- [x] 1.2 Add `refreshAccessToken()`: POSTs `/api/auth/refresh` (plain `fetch`, `credentials: 'include'`), returns `true`/`false`, and on success writes `localStorage.setItem(LAST_REFRESH_KEY, String(Date.now()))`.
- [x] 1.3 Add `coordinatedRefresh(dispatchedAt: number)`: if `refreshPromise` is set, return it (same-tab dedup). Otherwise set `refreshPromise` to a function that, if `navigator.locks` is available, calls `navigator.locks.request(AUTH_REFRESH_LOCK, async () => { ... })`; inside the lock, read `localStorage.getItem(LAST_REFRESH_KEY)` — if it's `>= dispatchedAt`, return `true` without calling the network (another tab's refresh, completed at or after this request was sent, guarantees the cookie is already fresh); otherwise call `refreshAccessToken()`. If `navigator.locks` is unavailable, fall back to calling `refreshAccessToken()` directly (same-tab-only dedup, documented residual risk on legacy browsers). Clear `refreshPromise` in a `finally` block. **`dispatchedAt` must be the caller's request-send timestamp, not a timestamp taken after the 401 is received** — see design.md's "Why `dispatchedAt`" note for why the send-time marker is required for correctness.
- [x] 1.4 Add `fetchWithAuthRetry(path, options)`: captures `dispatchedAt = Date.now()` immediately before the *first* `fetch` call (before it's known whether the request will 401). On a 401 whose `path` is not `/auth/login` or `/auth/refresh`, awaits `coordinatedRefresh(dispatchedAt)`; if it resolves `true`, retry the request exactly once and return that result (success or failure) to the caller. There is no further fallback on a second failure — a retry that still 401s after a real or skipped refresh is a genuine failure and must surface to the caller as-is (deliberately: an earlier draft called `refreshAccessToken()` directly here as a fallback, which bypasses both dedup layers and can recreate the cross-tab rotation race — do not reintroduce that).
- [x] 1.5 Rewire `apiRawFetch` to call `fetchWithAuthRetry` instead of `fetch` directly.
- [x] 1.6 Rewire `apiFetchNoBody` to call `fetchWithAuthRetry` instead of its own duplicated `fetch` call.
- [x] 1.7 Rewire `apiFetchForm` to call `fetchWithAuthRetry` instead of its own duplicated `fetch` call (keep the multipart/no-JSON-header behavior).
- [x] 1.8 Verify `reanalyzeMeal` (which calls `apiRawFetch` directly and branches on 502/412 before the generic `!res.ok` check) still gets a fully-retried response, since it goes through `apiRawFetch` → `fetchWithAuthRetry`.

## 2. Tests

- [x] 2.1 Add an E2E test in `e2e/tests/auth.spec.ts`: log in, then use `context.addCookies` to overwrite the `kin_access` cookie with an invalid value (simulating an expired/invalid access token while the real `kin_refresh` cookie from login is still valid), reload the dashboard, and assert the page stays on `/` (no redirect to `/login`) and renders authenticated content.
- [x] 2.2 Add an E2E test: log in, then clear/corrupt both `kin_access` and `kin_refresh` cookies, reload, and assert the page redirects to `/login` (refresh-failure path still works).
- [x] 2.3 Add a multi-tab E2E test: log in on one `page`, open a second `page` in the same `context` (Playwright contexts share cookies and `localStorage` across pages, modeling two tabs of one browser), corrupt the `kin_access` cookie so both pages' next request 401s, then trigger an authenticated request on both pages at roughly the same time. Assert: (a) both pages end up authenticated (neither redirects to `/login`), and (b) only one `POST /api/auth/refresh` network call is observed (via `page.route`/`context.route` interception counting requests to that path) — proving the losing tab did not resubmit the already-rotated refresh token. `navigator.locks` requires a secure context; `hcw-wip` is plain HTTP and `--unsafely-treat-insecure-origin-as-secure` did not work for its IP-based origin in this Chromium build (verified empirically), so this test proxies `hcw-wip` through a local `127.0.0.1` listener instead — `localhost` is unconditionally a secure context per spec, giving a reliable way to exercise the real Web Locks code path. Revised after review: the refresh-counting route and cookie corruption are registered before any reload (not after, closing a gap where an in-between refresh could go uncounted); both tabs wait for `networkidle` before corruption so no stray in-flight request from the initial load leaks into that window; the test asserts `isSecureContext`/`navigator.locks` directly so it fails loudly instead of silently degrading to the fallback path; and a `page.route` barrier holds each tab's first `GET /api/users/me` until both tabs' requests have arrived, forcing a genuine concurrent race instead of relying on lucky timing. Stress-tested 8/8 clean after the rewrite (an earlier version was shown to be flaky in review, reproducing `Expected: 1, Received: 0`).
