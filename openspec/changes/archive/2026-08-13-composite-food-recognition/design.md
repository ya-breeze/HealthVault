## Context

The photo food pipeline (`backend/pkg/server/food_upload.go`) runs two LLM calls per upload:

1. **Recognize** (`backend/pkg/vision/openai.go`) — sends the photo, returns structured `vision.Item{Name, Preparation, State, Brand, WeightGrams, Confidence}` per recognized item, or clarification questions if ambiguous. Its system prompt currently instructs the model to identify "each distinct food item," which is why a single composite dish reliably comes back as several ingredient-level items.
2. **Select** (`backend/pkg/vision/openai.go`) — a separate, text-only, stateless call. For each recognized item, `retrieveCandidates` builds a shortlist (custom food exact-name match, else Open Food Facts, else USDA — per `usda-nutrition-database`'s "Match Selection and Explicit Non-Match") and Select picks an index from that shortlist, or -1 for no match.

There is no "meal vs. dish vs. ingredient" level in the domain model — only `FoodMeal` (the logged photo) and a flat `FoodItem` list. `CustomFood` is a per-user, per-100g nutrient profile matched today only by exact case-insensitive name (`usda-nutrition-database` spec). Because Recognize already decomposes into ingredients, a saved composite `CustomFood` such as "Mexican vegetable mix" essentially never gets a chance to match — there is rarely a recognized item named that.

## Goals / Non-Goals

**Goals:**
- Make composite-dish naming the default outcome of Recognize, without removing its ability to decompose a visibly multi-component plate.
- Let a user-entered `CustomFood` (e.g., macros copied from a package label) get reused automatically on a later, differently-worded photo of a similar dish — including dishes eaten only monthly, not just daily repeats.
- Give every item *some* usable macro value even when nothing matches, rather than leaving it fully unresolved.

**Non-Goals:**
- No new user-facing granularity toggle for the initial upload. Recognize's own visual judgment decides granularity; the existing post-hoc Expert reanalysis path is untouched.
- No new "recipe" or "meal template" entity with an internal ingredient breakdown kept alongside a composite display name. `CustomFood`'s existing single-profile shape is reused as-is.
- No denormalized usage counters (e.g. `usage_count` on `CustomFood`). Frequency/recency is computed by querying existing `FoodItem`/`FoodMeal` rows (joined on `meal_id`, scoped to `confirmed` meals) at candidate-retrieval time; this app has one family's worth of data, so this join at upload time is cheap and avoids an extra write-path to keep consistent.
- No full rework of `CustomFood` matching or the standalone `CustomFood` management screen. The one addition in scope is a same-step "save as reusable food" action from the item-correction flow (decision 5) — not a broader redesign of how custom foods are created or managed.
- No third LLM call for macro estimation. It is folded into the existing Recognize call's response schema.

## Decisions

**1. Composite-dish naming is a prompt/schema change to Recognize, not a new mode.**
The system prompt changes from "identify each distinct food item" to instruct the model to name what it sees as a whole dish by default, and to only emit multiple items when it visually observes separately identifiable components (e.g., distinct piles on a plate, clearly separate foods). This is a judgment call left to the model on every photo — consistent with the user's explicit preference that granularity not be a manual per-upload choice.

**2. Custom-food candidate retrieval is widened, the exact-name lookup behaves exactly as it does today.**
`retrieveCandidates` keeps its current case-insensitive exact-name lookup unchanged: on a hit it returns a single-element candidate shortlist for that `CustomFood`, exactly as today — this is *not* a bypass of `Select` (see the correction to the "short-circuit" framing below); it's simply the only candidate offered, and Open Food Facts/USDA are not queried in addition to it. When the exact-name lookup does not hit, the candidate list `Select` receives is extended with the user's own custom foods ranked by a frequency-weighted score, added alongside whatever Open Food Facts/USDA candidates the existing brand-based routing would otherwise offer (not instead of them).

Ranking query: `FoodItem` already carries `user_id` directly (denormalized from its parent meal), so no join is needed to scope by user. What does require a join is `FoodMeal.status` and `FoodMeal.logged_at`, neither of which live on `FoodItem`: `SELECT custom_food_id, COUNT(*) AS usage_count, MAX(food_meals.logged_at) AS last_used FROM food_items JOIN food_meals ON food_items.meal_id = food_meals.id WHERE food_items.user_id = ? AND food_items.custom_food_id IS NOT NULL AND food_meals.status = 'confirmed' GROUP BY custom_food_id`. Two corrections from an earlier draft of this design: the join key is `meal_id`, not `user_id` (joining two tables on a repeated, non-unique column like `user_id` would fan out and multiply counts); and the query is scoped to `status = 'confirmed'` only — items on a still-`pending_review` meal already carry a `custom_food_id` from this very matching process, so counting them too would let an unverified, possibly-wrong automatic match reinforce its own future ranking before the user ever confirmed it was correct.

Score = `usage_count * frequency_weight + recency_score`, with frequency weighted higher than recency specifically so a dish confirmed once a month still outranks a one-off recent item; the exact weighting constants are an implementation detail tuned during `tasks.md`, not a spec-level requirement. Top-N (e.g. 5) by score are added to the candidate shortlist, and Select (already an LLM call reasoning over text descriptions, not exact string matching) picks among all of them. This means a "Mexican veggie mix" recognized item can still match a saved "Mexican vegetable mix" `CustomFood` even though the names differ, because Select reasons semantically, not lexically.

**3. Macro-source priority: custom food match > reference database match > model estimate.**
This is achieved by candidate composition, not a hard bypass at any tier — a correction from an earlier draft of this design, which overstated the exact-name case as binding "directly" without consulting `Select` at all. In reality, and unchanged by this proposal: an exact-name match produces a single-candidate shortlist that still goes through the same `Select` call as everything else (so it is not literally impossible for `Select` to reject it), and Open Food Facts/USDA are simply not queried in addition to it. For the frequency/recency-ranked case, the user's custom-food candidates are combined into the same shortlist as whatever Open Food Facts/USDA candidates the existing brand-based routing would already offer, and `Select` is instructed to prefer the user's own previously-used food when it is a reasonable match, since it reflects verified real-world macros rather than a generic reference profile. This keeps the pipeline at one candidate-retrieval pass and one `Select` call per batch, unchanged from today. The estimate fallback (decision 4) only fires when nothing in that combined shortlist — or no shortlist at all — resolves the item.

**4. New `macro_source = estimated` value, backed by a per-item profile persisted on `FoodItem`, not just Recognize's transient response.**
Recognize's structured output gains an optional per-item nutrient-profile field (calories, protein, carbs, fat, sugar, sodium, dietary fiber, per 100g), requested unconditionally so it's available whether or not a match is ultimately found. Unlike the first draft of this design, this profile is persisted on the `FoodItem` row itself as soon as the item is created — not kept only on the transient `vision.Item` value — for two reasons surfaced during review: (a) a clarification round (`ClarifyMeal`) reconstructs prior items from persisted `FoodItem` fields via a text-only follow-up call with no photo access, so it cannot regenerate an estimate; only the original photo-based Recognize call ever produces one, and it must survive the round-trip through `pending_clarification` to still be usable afterward; (b) a later weight-only edit (`PATCH .../items/{item_id}`) needs a per-100g profile to rescale from, the same way a `reference` item rescales from its bound source — a one-off computed value with no persisted per-100g basis cannot be safely rescaled.

At item-resolution time, this persisted estimate is used as the item's macros (scaled by weight) whenever nothing resolves through candidate selection — which, per the code as it exists today, is not only an explicit `Select` return of `-1`, but also: the shortlist for that item was empty and `Select` was never called for it at all (the current, and likely most common, path for a home-cooked dish with no brand and no USDA/OFF/custom-food match); a selection response error in non-strict mode; an out-of-range selected index; or a matched candidate whose profile lookup itself fails. All of these are today's paths to `macro_source = none`, and all of them are the intended fallback trigger, not just the literal `-1` case. When a match is found through any source, the persisted estimate is simply not used for macro purposes (it stays stored, harmlessly, for potential later reference). `MacroSource` becomes `reference | manual | estimated | none` (`none` now only occurs when Recognize itself produced no usable estimate for that item at all — e.g. a parse/validation failure on that field — which existing error handling already treats as a resolvable/reviewable state). `estimated` counts as a usable macro source for the meal aggregate, exactly like `reference` and `manual`.

**5. UI surfaces `estimated` distinctly, and offers to save a user's correction as a reusable `CustomFood` in the same step.**
The confirm-review screen, which already differentiates `reference`/`manual`/`none` items, gains a fourth visual treatment for `estimated` — communicating "AI guess, not a database fact" so the user is nudged to verify or correct it. Review surfaced that today's item-correction flow (`PATCH .../items/{item_id}`, `manual` macros) and `CustomFood` creation (`POST /api/food/custom`) are entirely separate and disconnected — a user who types in real macros from a package label on the confirm screen has no way to make that reusable without leaving to a different screen and re-entering the same name and values. This proposal adds a lightweight opt-in action to the existing correction flow — "also save this as a reusable food" — that creates the corresponding `CustomFood` in the same request, so decision 2's ranking can pick it up going forward. This is intentionally scoped down from a fuller "save-and-bind" redesign: the existing standalone `CustomFood` screen remains the primary place to manage saved foods (rename, fix a typo, delete); this just removes the friction of a duplicate re-entry at the moment a user has already typed the values once.

## Risks / Trade-offs

- **[Risk]** The vision model may not reliably observe the "decompose only when visually separate" instruction, either still over-decomposing or now under-decomposing genuinely mixed plates. → Mitigation: this is a prompt-tuning risk inherent to any vision-prompt change; validate against the existing model-calibration samples (`food-model-calibration`) before merging, and the Expert reanalysis path remains available as a correction if a specific meal comes out wrong.
- **[Risk]** Frequency/recency ranking could resurface a stale or wrong custom food if the user has renamed their eating habits. → Mitigation: Select still reasons over the item's actual recognized description, not a blind top-1 pick, and the user can always override on the confirm-review screen.
- **[Risk]** `estimated` macros are model guesses and may be inaccurate, and users might not notice the distinct UI treatment and log a bad estimate as-is. → Mitigation: this is a strict improvement over the current behavior of contributing zero macros for an unmatched item; the confirm-review screen already requires an explicit confirm step where the estimate is visible before it's aggregated.
- **[Trade-off]** Asking Recognize for a per-item macro estimate on every call (even when a match will likely be found and the estimate discarded) costs some extra output tokens on every request, in exchange for avoiding a third LLM call only on the fallback path. Given Recognize already returns structured per-item JSON, this is a marginal cost accepted for simplicity.
- **[Risk]** Without persisting the estimated per-100g profile on `FoodItem` (decision 4), a weight-only edit on an `estimated` item would have no basis to rescale from and would silently leave stale macros after the edit. → Mitigation: this is why the profile is persisted on the row instead of kept transient; the PATCH weight-only path is extended to rescale `estimated` items from it, the same pattern already used for `reference` items.
- **[Risk]** An item that enters a clarification round loses access to a fresh macro estimate, because the follow-up call is text-only with no photo access. → Mitigation: the *original* Recognize call's estimate is persisted on the row at creation time (decision 4), before any clarification round begins, and is reused as the fallback after clarification concludes if nothing still matches — it does not need to be regenerated.

## Migration Plan

A database migration is required: `FoodItem` gains a persisted per-100g estimated-nutrient-profile field (nullable — most items resolve to a real match and never populate it). `macro_source` itself remains a plain string-valued GORM field, so the new `estimated` value needs no schema change on its own. This ships as a single backend+frontend deploy with no phased rollout — mismatched behavior between an old frontend and a new backend during deploy would only manifest as an unstyled/unlabeled (but functionally correct) `estimated` item, not a broken state, since `estimated` items still carry real numeric macros and existing generic item rendering already displays any macro values.
